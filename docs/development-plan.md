# PleosMate 개발 계획

## 1. 개발 목표

[PRD](prd.md)의 핵심 여정인 ‘동료 선택 → 주차 후 활동 → 성장 → 기억과 재방문’을 하나의 완결된 경험으로 구현한다. 차량 신호와 위치를 사용하는 기능은 지원 여부와 실패 처리를 먼저 설계하고, 사용자가 저장했다고 믿는 기록을 안정적으로 보관하는 것을 출시 기준으로 삼는다.

단계는 제품 경험과 의존성에 따라 구성한다. 일정은 팀 규모와 차량 시험 환경을 확보한 후 산정하며, 각 단계는 아래 완료 기준을 충족한 뒤 다음 단계로 넘어간다.

## 2. 개발 단계와 산출물

| 단계 | 핵심 질문 | 주요 작업 | 산출물·완료 기준 |
| --- | --- | --- | --- |
| 1. 문제·경험 설계 | 주차 후 어떤 순간에 앱을 열 이유가 생기는가? | 대상 사용자와 시나리오 정의, 첫 성공 흐름, 주요 화면과 보상 정책 설계 | PRD, 화면 흐름, 시제품; 첫 활동을 설명할 수 있는 일관된 사용자 여정 |
| 2. 차량 연결 검증 | 필요한 상태를 신뢰할 수 있게 읽을 수 있는가? | 주차·UX 제한, 권한, 창문·도어·차량 정보·위치 지원 확인 | 지원 기능 표와 기술 검증 시제품; 정상·미지원·권한 거부를 구분 |
| 3. 동료와 성장 기반 | 사용 경험이 다음 실행으로 이어지는가? | 동료·이름 선택, 홈, XP·레벨, 저장·복원, 공통 안내 | 동료 선택부터 첫 성장까지 연결; 재실행 후 확정 상태 보존 |
| 4. 일상 미션 | 짧은 주차 시간에 성취할 수 있는가? | 차량·경험 미션, 일일·주간 규칙, 반응, 취소·중복 방지 | 미션 완료와 보상이 일치; 주행 전환·중복 요청에서 오지급 없음 |
| 5. 여행과 기억 | 방문·재방문이 의미 있게 쌓이는가? | 지도 계층, 현재 동네 판정, 조각 세 단계, 여정·메모·초안 | 현재 위치 확인부터 수집·기억 저장까지 연결; 경계·재방문·재시작 검증 |
| 6. 도감과 자기표현 | 쌓인 경험을 돌아보고 애착을 느끼는가? | 배지·이야기·기억 열람, 꾸미기, 반응 음성, 설정·초기화 | 완료 기록과 표시가 일치; 해금·변경·삭제 흐름을 사용자가 이해 |
| 7. 통합 검증·출시 | 처음부터 끝까지 믿고 사용할 수 있는가? | 기능·저장·차량 호환·사용성 검증, release 패키징, 제출 문서 | 수용 기준 확인표, 알려진 제한, 서명 APK와 대응 소스·문서 |

## 3. 작업 묶음과 의존성

### A. 공통 기반

온보딩, 홈·여행·미션·도감·설정 탐색, 공통 화면 상태와 메시지, 차량 연결 상태를 구성한다. 성장·프로필·기억의 보관 책임을 구분하고 저장 실패 및 재실행 동작을 정한다.

성장 규칙은 화면과 독립적으로 판단할 수 있게 설계한다. 완료 기록과 보상 표시가 서로 다른 기준으로 어긋나지 않도록 하며, 기능 변경 시 이전 저장 데이터를 읽는 정책을 포함한다.

### B. 차량 미션

상태 읽기와 제품의 완료 판단을 분리한다. 지원 기능·값 범위·단위·권한을 확인한 후 각 미션의 시작·완료·중단 조건을 정의한다. 미지원 기능에 대한 대체 안내를 준비한다.

미션 시작뿐 아니라 완료 직전에도 주차 상태를 확인한다. 화면 이탈·취소·차량 연결 해제 뒤 도착한 결과는 반영하지 않는다. 저장이 성공한 이후에 확정 보상과 완료 메시지를 표시한다.

### C. 여행·지역 수집

출처와 사용 조건이 명확한 행정구역 데이터를 확보하고 지도 탐색과 현재 위치 판정을 연결한다. 동네별 세 조각, 하루 한 조각, 첫 시·도 보상 정책을 구현한다.

지역 검증은 일반 내륙, 시·도 경계, 좁은 동네, 섬, 여러 폴리곤으로 이루어진 지역을 포함한다. 내부 좌표가 존재하는지와 차량이 실제 접근할 수 있는지를 함께 본다. 잘못된 동네 지급과 정상 방문 거절을 모두 측정해 경계 정책을 결정한다.

### D. 기억·도감·꾸미기

관찰한 여정과 직접 작성한 기억을 구분하고, 초안 복원·수정·삭제를 제공한다. 배지와 성장 이야기는 저장된 성취에 맞춰 표시한다. 동료 변경, 꾸미기 변경, 앱 재실행이 기존 성장을 훼손하지 않게 한다.

### E. 제출·배포

필수 README, 데이터 출처·라이선스, 지원 환경, 알려진 제한을 정리한다. release APK의 서명·설치·시작을 확인하고 최종 소스와 산출물의 대응을 기록한다. APK가 저장소 업로드 제한을 넘으면 GitHub Release에 첨부한다.

## 4. 검증 전략

| 검증 층위 | 확인 대상 | 통과 기준 |
| --- | --- | --- |
| 규칙 | XP·일일/주간 중복·최대 조각·기억 유효성 | 같은 입력과 완료 기록에 일관된 결과, 경계 조건 처리 |
| 저장 | 성장·프로필·여정·초안 | 저장 후 재실행·업데이트 유지, 실패 시 기존 기록 보호 |
| 차량 연결 | 권한·미지원·오래된 값·주차 전환 | 잘못된 상태에서 성공·보상 처리하지 않음 |
| 화면 통합 | 첫 만남부터 수집·도감까지 | 상태·안내·보상이 일치하며 취소·뒤로가기 동작 예측 가능 |
| 지역 | 동네 판정·경계·섬·재방문 | 오지급과 수집 불가 사례를 분류하고 지원 범위 결정 |
| 사용성 | 첫 성공·다음 행동·재방문 이유 | 관찰된 막힘을 정리하고 중요 문제 해결 후 재평가 |
| release | 빌드·서명·설치·실행·환경 | 제출 APK와 소스 버전, 설명 문서가 동일 대상을 가리킴 |

날짜별 수집은 날짜 전환·같은 날 반복·최대 슬롯·재실행을 조합해 확인한다. 지역별 첫 수집과 공통 추가 슬롯 규칙을 나누어 검증하되, 대표 표본 시험을 전수 시험으로 표시하지 않는다. 실제 차량 결과와 에뮬레이터 결과는 구분해 기록한다.

## 5. 주요 위험과 대응 계획

| 위험 | 사용자에게 생길 문제 | 대응 |
| --- | --- | --- |
| 차종별 신호 차이 | 미션을 수행할 수 없거나 조건을 오해 | 지원 기능 확인, 미지원 안내, 환경별 검증 표 |
| 주행 중 상태 전환 | 제한 상황에서 활동·보상 지속 | 시작·완료 재확인, 진행 중 작업 취소 |
| 경계·위치 오차 | 방문한 동네를 못 받거나 다른 동네 지급 | 위치 신선도와 불확실성 처리, 지역 유형별 검증 |
| 중복·날짜 변경 | 성장 규칙의 일관성 훼손 | 완료 키와 날짜 정책 명확화; 금전 보상 도입 전 신뢰 모델 재설계 |
| 저장 실패·업데이트 | 성장과 추억 소실 | 저장 확정 순서, 실패 복구, 데이터 호환 검증 |
| 공동 차량 사용 | 개인 기록 노출에 대한 오해 | 보관 범위 안내, 삭제 기능, 사용자 분리 필요 조사 |
| 수집 피로 | 완료 압박이나 불필요한 이동 | 일상 방문 중심 설계, 미완료 부담을 줄이는 안내 |

## 6. 출시 판단 기준

첫 실행부터 동료 선택, 유효 활동 완료, 성장 확인, 기억 열람까지 연결되어야 한다. 주차 제한·권한 거부·미지원·저장 실패에서 사용자에게 가능한 다음 행동을 제시해야 한다. 확정된 기록은 재실행과 업데이트 후 유지되어야 한다.

지원 지역과 차량 환경을 명시하고, 사용을 막거나 잘못된 보상을 만드는 문제는 해결 또는 지원 범위 조정 후 출시한다. 최종 APK·소스 커밋·태그·Release·README가 같은 버전을 설명하는지 확인한다.

## 7. 출시 후 발전 방향

초기 사용 관찰에서는 첫 성공 시간, 이탈 구간, 다시 열 이유를 우선 확인한다. 반응·꾸미기·기억 콘텐츠는 실제로 사용자가 가치를 느낀 흐름부터 확장한다.

계정과 동기화는 차량 공동 사용·기기 교체 요구를 확인한 뒤 설계한다. 유료 꾸미기와 플랫폼·관광 제휴는 지불 의향 및 파트너 역할을 검증한 뒤 진행한다. 혜택에 금전 가치가 생기는 경우 완료 이벤트·시간·위치의 신뢰와 정산 책임을 별도로 다룬다.

### 리워드·B2B 확장 단계

| 단계 | 주요 작업 | 다음 단계 진입 기준 |
| --- | --- | --- |
| 제휴 가설 검증 | 주유·충전·정비·세차 파트너의 고객 확보·재이용 요구와 사용자 할인 선호 조사 | 제휴 대상, 혜택 재원과 양측 기대 성과 합의 |
| 리워드 설계 | 성장 XP와 별도 리워드 정의, 지급 조건·한도·유효기간·취소 정책 수립 | 사용자 안내와 제휴 계약의 조건 일치 |
| 발급·사용 기반 | 계정, 서버 완료 검증, 중복 방지, 쿠폰 발급·사용 연동, 정산 기록 설계 | 지급·사용·취소·실패 복구 흐름과 비용 추적 검증 |
| 한정 제휴 실험 | 소수 제휴처에서 주유비 또는 충전 할인 캠페인 운영 | 사용률·재이용·건당 비용·사용자 재방문으로 지속 가능성 판단 |
| B2B 확대 | 제휴사 캠페인 관리·성과 보고, 완성차·플랫폼 고객 프로그램 연계 | 운영·정산 안정성과 파트너별 사업성 확인 |

캠페인 성과를 측정할 때 추가 이동이나 연료 소비 증가를 목표로 삼지 않는다. 제휴사에 제공할 정보는 혜택 사용과 성과 확인에 필요한 범위로 정하고, 개인 기억과 상세 이동 기록은 캠페인 보고에 포함하지 않는다.

구현 구조는 [아키텍처](architecture.md), 실제 시험 결과와 미해결 항목은 [검증 기록](verification-status.md)에서 관리한다.
